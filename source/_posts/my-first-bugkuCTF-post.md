## 前言
作为一个写博客的新手，想练习如何用 Hexo 写博客，借此机会，讲讲我做 bugkuCTF 题目时的解题过程。这是我在 Bugku 做的第一道 Web 题，卡在「为什么 1e 既不是数字、又能等于 1」上。这篇把当时的思路和踩的坑记下来。

## 题目信息
| 项目 | 内容 |
| --- | --- |
| 平台 | Bugku |
| 题目 | 矛盾 |
| 类型 | Web / PHP 弱比较 |
| 考点 | 弱类型比较（`==`）、`is_numeric` 的边界 |

## 漏洞的原理
打开环境，得到以下代码：
```php
<?php
$num=$_GET['num'];
if(!is_numeric($num))
{
    echo $num;
    if($num==1)
        echo 'flag{**********}';
}
```
分析代码逻辑，`is_numeric($num)`判断num是不是数字，如果不是数字，则进入判断语句，先输出num，再判断num是否等于1，如果等于1，则输出flag。这里存在明显矛盾，因为要得到flag，需要num等于1，而1又是数字，在第一条判断中就被否决了。但是注意第二个判断条件用的是`==`弱比较，可以被绕过。

## 漏洞的利用与绕过
`is_numeric("1e")` 返回 false，因为 `1e` 不是合法数字——科学计数法要求 `e` 后面必须跟指数（如 `1e1`）。残缺的 `1e` 骗过了第一层；而在 `==` 比较时，PHP 会把它转成数字 1，`"1e"` == 1 成立，于是骗过第二层。从而输出flag。所以payload可以这么写：
```text
?num=1e
```

页面回显（`echo $num` 先把输入原样打出来，紧跟着才是 flag）：
```text
1eflag{**********}
```

常见弱比较对照表：
```php
var_dump("1e"  == 1);      // true  ← 本题用的
var_dump("1"   == "01");   // true
var_dump("10"  == "1e1");  // true  两个数字字符串，数值比较
var_dump(100   == "1e2");  // true  100 vs 100.0
var_dump(0     == "a");    // true（PHP 7）；PHP 8 起为 false
```

注意：PHP 8.0 收紧了「字符串和数字比较」的规则，非规范数字字符串不再被转成数字。如果你在本地复现失败，先 php -v 看版本——这类 payload 在 PHP 8 上会失效，而 Bugku 的靶场一般还是 PHP 5/7。

## 漏洞的修复
我在做的时候想的是把`==`弱比较换成`===`强判断，后面问 AI 后才发现，`===`强判断会把正常功能也改坏：
```php
$num = $_GET['num'];   // 永远是字符串
if ($num === 1) {}     // "1" === 1 恒为 false，正常输入也进不去
```

因为 `===` 比较类型，而 `$_GET` 取出来永远是字符串，字符串永远不等于整数。正确的修复是先校验再比较：
```php
<?php
$num = filter_var($_GET['num'] ?? '', FILTER_VALIDATE_INT);
if ($num !== false && $num === 1) {
    echo 'flag{...}';
}
```

或者：
```php
if (!is_numeric($num)) { /* 直接拒绝 */ }
$num = (int)$num;
if ($num === 1) { ... }
```

## 小结
学到了`==`是弱比较，存在安全问题。遇到想不通的点，我会去问 AI 或翻 PHP 手册，往往能挖出「题目之外」的知识——这次就多学了两点：
1. PHP 版本更新后，非规范数字字符串不再被转成数字。
2. 这道题源码中还存在一个XSS漏洞，这是我之前没意识到的，`echo $num` 直接把用户输入原样输出，这本身就是一个反射型 XSS。需要对 `echo $num` 做转义。下次做CTF题时要注意认真分析源码，可能会发现不止一个漏洞。
